A Testable Local Semantic Layer

First draft · research as of 2026-10-01

I started with a working job-search workflow. It reads alerts, extracts facts, checks history, applies rules and identifies what needs attention. Most of this is familiar Python backend work: parsing, lookups, exact comparisons and state transitions. The expensive part is interpreting language. Does an advertised role include managing people? Does a passage promise sponsorship, deny it, or say nothing? Does an answer supply the information requested and support what it claims?

I wanted those semantic operations to become cheap, local functions I could test. My first attempt compressed too much into one call: I gave Laya a workflow and asked it to choose drop or survive. It returned survive for all 300 historical roles. Perfect survivor recall was available from a constant function. I had obtained an allowed answer without transferring the workflow. That failure is the starting point of this book. Evidence E01

The question became more precise: can a small local model provide useful observations while Python retains policy, provenance, history and final authority? I call that proposed component “System 1.” This names an operational role, not a claim that a checkpoint reproduces human cognition. A generative worker or reviewer sometimes occupies the complementary “System 2” role. Neither name is an evaluation result.

I also want my explanations to earn their complexity. A cheap mental model can be enough to make the next engineering decision. When an observed failure exposes its limits, I can refine it. That deliberate simplification differs from accepting unsupported model predictions. Predictions require an error budget: which mistakes matter, what their consequences are, and how much useful recall or coverage the component must retain. “Never answer” and “always assert” can both fail the contract.

Diagram: The proposed boundary lets a local model report an observation while Python checks scope and applies policy; uncertainty remains a reviewable state.

Eight branches developed around this question. The first is the workflow boundary: which judgments can be separated from policy? The second is the model interface: bounded options, extracted spans, claim support and passage relevance are different measurements. The third is zero-shot behavior: what changes when I alter wording, keys, distractors or evidence? These branches help me decide whether an apparent model failure is partly a poorly specified request.

The fourth branch defines answer quality. Requested-information coverage, evidence support, responsiveness and compliance can disagree, so I need separate judgments. The fifth asks where their reference labels come from. Independent model annotations improve the evidence available for debugging, but remain proxy references. Shared mistakes and disagreements survive a vote. Neither a fluent explanation nor model confidence supplies human ground truth.

The sixth branch puts annotation on my GPU. Spark finished more requests and ran faster when I disabled native thinking, but several judgments assessed its own output format instead of the target answer. The seventh branch preserves these failures as richer candidate supervision: source lineage, separate votes, missing labels, failure tags and proposed evidence spans. It also forces a distinction between evaluation masks, loss masks, attention masks and Laya’s option-position [MASK] tokens. The eighth sets the gate: what evidence would justify admitting any observation into the active harness?

Diagram: These conceptual links map borrowed tools to questions around one bounded semantic layer; they do not show a chronological pipeline or imply every technique is implemented.

These branches overlap. Better references can expose a prompt defect. A better prompt might remove the need for adaptation. A cheap local judge might generate candidate labels while creating a new adjudication burden. The chapter sequence makes this investigation readable; it does not imply a linear chronology from failed prompt to successful fine-tuning.

At this release, diagnostic runs, a wider native-interface comparison, prompt probes and a Spark pilot exist. No task fine-tuning has started. Synthetic optimizer and memory probes establish limited feasibility, not learned task performance. The expanded prompt study has now completed development and frozen-selection confirmation: results are mixed, with no broad prompt recipe established. The general annotation factory remains a parked specification. None of these experiments has replaced the production workflow.

This is the canonical authored book draft. Earlier articles and experiment notes remain research sources, rather than chapter copies to synchronize. The public evidence appendix gives short identifiers, denominators and limits; it deliberately does not expose private inputs or machine locations.
